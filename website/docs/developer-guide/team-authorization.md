# Team authorization — staged implementation, activation and rollback

**Staged only; disabled by default. No live protection is claimed.** The
acceptance tests use synthetic Discord IDs, temporary homes and inert provider
backends. Activation, real-account inventory and live rollback require a
separate operator decision.

## Design and actual enforcement

The posture is **ordinary team work open; three flat denials only**. Active
registered members can use terminal, shell, code execution, host file tools,
process tools, browser execution, cron, delegation, connectors, image/video
generation and ordinary project editing, including their own supplied local
media. An unmapped tool or connector is ordinary work: `toolActions`,
`connections` and `spendingCaps` may all be empty without blocking it. Only
credentials, Charles' personal mailbox, and browser credential-entry /
machine-information reads are denied, with flat `I can't …` wording and no
approval route. Mapped business actions still retain role, account and spend
checks. Unknown, revoked or inactive identities, an unlisted transport scope,
malformed policy and missing identity on a governed surface still fail closed
(the register is the identity boundary). A Discord display name, role label or
model-supplied requester is never identity authority.

The integration binds `SessionSource` before gateway agent creation and carries
identity (not grants) into dispatch, execution, delegated and scheduled work.
Discovery filtering is advisory; the real arguments are checked again after
transformation and at the execution boundary. Inline tools, MCP dispatch,
connector batches, cron replay and cron direct delivery have their own checks.
Revocation and policy changes are re-read rather than changing the cached system
prompt midway through a conversation.

- Terminal, shell, code execution, host file tools, process tools, cron,
  delegation, desktop/computer tools and browser execution are ordinary member
  work. The protected classifications (credentials, personal mailbox) cannot be
  removed by a mutable `toolActions` mapping.
- Browser execution is available to active members; the argument guard rejects
  login/credential-entry and machine-information requests.
  Initial URLs must resolve publicly, including on local/sidecar backends and
  when the owner's global private-URL toggle is enabled. The same public-only
  rule applies to member URL fetches outside the browser verbs (`web_extract`,
  vision/image HTTP resolvers, and the shared `is_safe_url` / connect-time
  SSRF path). Unverifiable DNS fails closed even with a proxy. Redirect results
  and current-page probes are checked; private/unverified results are withheld.
  Camofox is checked too and never gives a member the owner's VNC link. These
  are URL/content guards, not a browser network sandbox: they do not promise to
  prevent every subresource connection, DNS rebind or contact made before a
  redirect is detected. A browser with network-level isolation is an additional
  activation prerequisite.
- Personal/infrastructure/billing connections deny non-owners when a mapped
  `toolActions` row names them. An unmapped connector is not denied by the team
  layer; the connector gateway's own connection state still applies.
- A secure-owner approval records an exact operation/resource/audience and TTL.
  It does not give a teammate ordinary owner authority. Protected tool execution
  remains denied to non-owners even when they present an approval ID.
- Staff history is scoped to its originating author and destination. Management
  oversight requires authenticated management and an explicitly listed surface;
  it is audited and excludes Charles' private history.
- A staff DM summary is publishable only with its author's transport-verified
  consent for the exact source, summary bytes/hash and destination. A manager
  cannot consent for the author. Private-origin connector writes bind the entire
  canonical provider payload and a source derived from the verified requester,
  not model-supplied source labels or optional summary fields. Renaming arguments
  does not bypass consent. Delivery remains origin-scoped; no team-wide notices
  are generated by this control layer.
- **Mem0 is the only external memory provider isolated by this integration.**
  It uses a member namespace and verifies ownership before update or deletion.
  Fixed global Mem0 IDs do not override the namespace. Requester context is
  retained for background memory work. This does not establish isolation for
  Honcho, Hindsight or other memory plugins; those must be disabled for governed
  team traffic before activation until equivalent isolation has been tested.

- Delegated task images, direct image resolution, outgoing messages and gateway
  media delivery treat a teammate's own local media as ordinary work; the
  remaining media guard denies only principals the policy has already refused
  (revoked/inactive/unlisted scope/malformed policy), before any reader. Public
  and inline inputs keep their existing size/type checks. The requester-scoped
  media provenance cache was removed with the rest of the owned-media gates.

## Configuration and register schema

Enablement is in **`$HERMES_HOME/config.yaml`**, not in the register:

```yaml
team_authz:
  enabled: false
  mode: enforce
  governed_platforms: [discord]
  # Populate only from verified private transport surfaces before activation.
  secure_owner_surfaces: []
```

No block, or `enabled: false` with `mode: enforce`, retains base behaviour,
including its lack of these team protections. A malformed enabled config or
register fails closed. Removing the enabled register does not disable the guard.

In an isolated synthetic home, `mode: shadow` is active even with `enabled: false`:
it audits inbound messages and would-allow/would-deny decisions, but does not
execute tools or reserve spend. Shadow is evidence collection, not live
protection or authorization to replay against real accounts.

The register is **`$HERMES_HOME/team_authz/register.json`**. Its actual top-level
fields are shown below. This example is synthetic, not an activation roster:

```json
{
  "schemaVersion": 1,
  "policyVersion": "synthetic-v1",
  "guilds": ["910000000000000001"],
  "members": [
    {"discordUserId": "900000000000000001", "memberKey": "owner",
     "role": "owner", "status": "active", "approvedBy": "synthetic-owner",
     "approvedAt": "2026-01-01T00:00:00+00:00"},
    {"discordUserId": "900000000000000003", "memberKey": "am",
     "role": "account_manager", "status": "active", "approvedBy": "synthetic-owner",
     "approvedAt": "2026-01-01T00:00:00+00:00"}
  ],
  "roles": {
    "owner": {"capabilities": ["owner.host", "register.change"]},
    "account_manager": {"capabilities": ["basic", "web.read", "ghl.manage"]}
  },
  "toolActions": [
    {"pattern": "connectors__ghl__charge", "action": "ghl.manage",
     "connectionId": "synthetic-business", "accountArg": "account",
     "amountArg": "amount", "currencyArg": "currency"}
  ],
  "connections": [
    {"id": "synthetic-business", "connector": "ghl", "account": "synthetic-account",
     "ownerClass": "business", "actions": ["ghl.manage"]}
  ],
  "spendingCaps": [
    {"memberKey": "am", "connectionId": "synthetic-business",
     "account": "synthetic-account", "currency": "USD", "period": "month",
     "amount": 100, "scope": "", "approvedBy": "synthetic-owner"}
  ],
  "oversight": {"destinations": []},
  "ownerApprovals": [],
  "sharingConsents": []
}
```

`status` is `active`, `inactive` or `revoked`. Cap periods are `day`, `week` or
`month`. An amount-mapped action with no matching approved cap denies; a negative,
non-numeric or non-finite amount denies. Cap accounting serializes the final execution reservation and audit append;
discovery and preflight checks do not consume spend. Reservations are
conservative authorizations, not provider-confirmed settlement. There is no
invented live default amount.

`ownerApprovals` and `sharingConsents` are written by the trusted control-plane
functions in `agent/team_authz_owner.py` and `agent/team_authz_sharing.py`, never
by model-provided approval flags. Register writes are atomic and freshness-
checked. Changes are observed at subsequent authorization checks.

## Audit and privacy

`$HERMES_HOME/team_authz/audit.jsonl` records inbound requester ID, member key,
transport/destination references and time before tools; per-tool decisions have
an action and reason. Inbound text is represented by SHA-256 and byte length,
not copied verbatim. Rejected amount/currency values are not copied as arbitrary
text. Full message bodies, tool argument dictionaries, passwords and tokens do
not belong in this log.

Consent, oversight, register-change and secure-owner approval/check events share
the ledger. Each row carries `prev` and `h`; append is serialized across threads
and processes. `audit_verify()` checks the chain against a durable
`audit.head.json` checkpoint. Missing or edited rows and tail truncation relative
to the checkpoint fail closed before a new allow. This cannot defeat a privileged
administrator replacing both files with an older matched pair. POSIX file
permissions are owner-only (0600); Windows ACL hardening and a production-volume
audit drill remain activation work.

There is no permissive shadow-mode switch that executes denied operations.
Observation/probe runs use synthetic requests and inert backends. Enabling the
layer enforces denials, not just audit warnings. Approval-check events are proof
of policy checks, not proof that an actual vault was unlocked or a provider call
succeeded.

## Acceptance coverage

Run the integrated suite **and all `test_team_authz_*` component suites**. The
single integrated file is not a replacement for execution-path coverage:

1. Real Discord `Platform`/`SessionSource` binding, unknown identity and gateway
   turn gate; disabled/base and missing-context component regressions.
2. All seven recorded roles: allowed mapped action and denied unlisted transport
   scope; every non-owner also denied a mapped outside-role action. The owner
   intentionally has no fabricated outside-role restriction. Positive controls
   cover a registered non-owner running terminal and an empty-mapping connector.
3. Protected tools (credentials, personal mailbox, browser login/machine info),
   secure-owner provenance, immutable remaps, personal connections, manager
   approval and owner-impersonation attacks; unknown requesters stay refused with
   the flat wording, while the owner remains allowed.
4. Real session DB/search ownership, attachments/output and per-member Mem0
   isolation, including update/delete and background paths.
5. Authenticated, destination-scoped oversight and exact-byte author consent;
   mismatched summary/destination and revoked consent deny before dispatch.
6. Connector account/class checks for mapped rows, discovery, deferred
   and inherited MCP, argument transforms, inline execution and batch checks;
   unmapped connectors dispatch as ordinary work.
7. Approved caps, missing/wrong cap inputs, aggregate and concurrent accounting.
8. Revocation between discovery/creation and tool, delegated child, queued/replay
   or cron/direct-delivery execution; deny before the protected backend.
9. Two synthetic homes in A-B-A order, repeated in fresh subprocesses, with
   multiplex mode active and context-local homes overriding the process home.

The new integrated file also asserts audit order/redaction and per-tool identity.
Tests spy on the provider boundary so a denied operation must produce zero calls;
positive controls prove the ordinary path is not simply disabled.

## Safe rollback

**Disabling authorization restores base behaviour; it does not keep staff safe.**
Do not switch `team_authz.enabled` off while continuing to accept team traffic.

1. With separate activation/rollback authority, first close governed staff ingress
   at the gateway/routing boundary. Keep it closed throughout rollback.
2. Restore the exact-byte known-good code/config/register backup (or set
   `team_authz.enabled: false` only within the approved owner-only recovery lane).
3. Restart only with explicit runtime authority. Verify fresh owner-only/base
   behaviour and run the synthetic acceptance gates against the restored state.
4. Reopen staff ingress only after the restored protection, verified roster and
   connection inventory have passed the real-surface checks. A disabled guard
   is never evidence that staff isolation is working.

This implementation did not modify live config, credentials, accounts, browser
sessions, gateway processes or staff traffic routing.
